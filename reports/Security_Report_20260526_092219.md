- **엔드포인트:** `POST /api/login`
- **발견 횟수:** 2건


## 🔍 세부 인스턴스 분석 (1/2)


### 2. 📍 소스코드 매핑 정보

### 3. 🧠 지능형 보안 분석

- **최종 판별:** 🔴 정탐 (Vulnerable)
- **분석 확신도:** `100.0%`
- **CVSS v3.1 스코어:** **9.8** (`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`)

#### [판단 요약]
> 로그인 API에서 사용자 입력값(`email`, `password`)을 안전하게 처리하지 않고 SQL 쿼리문에 직접 삽입하여 발생하는 **SQL Injection 취약점**입니다. 공격자는 이 취약점을 이용해 인증을 우회하고 데이터베이스의 모든 정보에 접근, 수정, 삭제할 수 있습니다. DAST 스캔에서 확인된 데이터베이스 오류 메시지는 공격 페이로드가 성공적으로 쿼리 구문을 변경했음을 명확히 입증합니다.

#### [핵심 증거 포인트 (Evidence)]

- ✅ DAST 스캔 결과, `sqlite3.OperationalError` 응답이 확인되어 공격 페이로드가 데이터베이스 쿼리 구문을 파괴했음을 입증합니다.

- ✅ 소스코드(`routes/login.ts`)에서 `req.body.email`과 `req.body.password` 값이 아무런 검증이나 이스케이프 처리 없이 SQL 쿼리문에 직접 삽입되고 있습니다.

- ✅ 파라미터화된 쿼리(Parameterized Query)나 ORM(Object-Relational Mapping)과 같은 안전한 데이터베이스 접근 방식이 사용되지 않았습니다.


#### [심층 분석 과정 (Reasoning Process)]
<details>
<summary>논리적 추론 단계 보기 (Chain of Thought)</summary>


1. 1. DAST 응답 분석: `sqlite3.OperationalError`는 사용자 입력이 SQL 쿼리에 영향을 미쳐 구문 오류를 발생시켰음을 나타내는 명백한 증거입니다.

2. 2. 소스코드 분석: `login.ts` 파일의 12번째 줄에서 `req.body.email`과 `req.body.password`가 템플릿 리터럴을 통해 쿼리 문자열에 직접 결합되는 것을 확인했습니다.

3. 3. 취약점 검증: 입력값에 대한 이스케이프(escaping), 입력값 검증(validation), 또는 파라미터화된 쿼리(prepared statements)와 같은 방어 메커니즘이 전혀 존재하지 않음을 확인했습니다.

4. 4. 결론: DAST 결과와 SAST 분석이 완벽하게 일치하며, 이는 전형적인 SQL Injection 취약점으로 인증 우회가 가능하여 정탐으로 판별합니다.

</details>

### 5. 🛠️ 시큐어 코딩 패치 제안

#### [패치 가이드]

- 1. 사용자 입력값을 SQL 쿼리문에 직접 삽입하는 동적 쿼리 생성 방식을 제거했습니다.

- 2. SQL 쿼리문에 플레이스홀더(?)를 사용하고, 사용자 입력값은 별도의 파라미터 배열로 전달하는 파라미터화된 쿼리(Parameterized Query) 방식으로 변경했습니다.

- 3. 이 방식은 데이터베이스 드라이버가 입력값을 데이터로만 취급하고 실행 코드로 해석하는 것을 방지하여 SQL Injection 공격을 원천적으로 차단합니다.


#### [수정 제안 코드]
```typescript
app.post('/api/login', (req, res) => {
  const query = 'SELECT * FROM Users WHERE email = ? AND password = ?'
  const params = [req.body.email, req.body.password]
  db.query(query, params).then(user => { ... })
})
```

#### [QA 검수 결과]
- **검수 통과:** ✅ 통과
- **피드백:** SQL Injection 취약점을 해결하기 위해 파라미터화된 쿼리를 적용한 것은 올바른 조치입니다. 비즈니스 로직에 영향을 주지 않으면서 보안성을 크게 향상시켰습니다. 다만, 코드의 근본적인 로직에서 비밀번호를 평문으로 비교하는 것은 매우 위험합니다. 데이터베이스 유출 시 모든 사용자 계정이 탈취될 수 있으므로, 반드시 bcrypt와 같은 검증된 알고리즘으로 비밀번호를 해싱하여 저장하고 비교하는 로직으로 개선해야 합니다.

### 5. 🛠️ 시큐어 코딩 패치 제안

#### [패치 가이드]

- 사용자 입력값을 SQL 쿼리에 직접 결합하는 기존 방식은 SQL Injection 공격에 취약합니다.

- 이 문제를 해결하기 위해, SQL 쿼리에서 사용자 입력이 들어갈 자리를 플레이스홀더(placeholder)로 대체하는 파라미터화된 쿼리(Parameterized Query)를 도입했습니다.

- 기존의 동적 쿼리 문자열 `SELECT * FROM Users WHERE email = '${req.body.email}' AND password = '${req.body.password}'`를 플레이스홀더(`:email`, `:password`)를 사용한 정적 쿼리 템플릿 `SELECT * FROM Users WHERE email = :email AND password = :password`으로 변경했습니다.

- 사용자 입력값(`req.body.email`, `req.body.password`)은 `replacements` 옵션을 통해 쿼리와 안전하게 분리되어 데이터베이스 드라이버에 전달됩니다. 이를 통해 데이터베이스 엔진은 사용자 입력을 실행 코드가 아닌 순수한 데이터 값으로만 해석하여 SQL Injection을 원천적으로 차단합니다.


#### [수정 제안 코드]
```typescript
app.post('/api/login', (req, res) => {
  const query = 'SELECT * FROM Users WHERE email = :email AND password = :password'
  db.query(query, {
    replacements: {
      email: req.body.email,
      password: req.body.password
    }
  }).then(user => { ... })
})
```

#### [QA 검수 결과]
- **검수 통과:** ❌ 재검토 필요
- **피드백:** SQL Injection 취약점은 파라미터화된 쿼리를 사용하여 성공적으로 해결되었습니다. 그러나 로그인 로직에 더 심각한 보안 문제가 남아있습니다. 패스워드를 평문으로 데이터베이스에 저장하고 비교하는 것은 매우 위험합니다. 사용자의 패스워드는 반드시 bcrypt나 Argon2와 같은 강력한 알고리즘을 사용하여 솔트(salt)와 함께 해싱하여 저장해야 합니다. 인증 로직은 다음과 같이 수정되어야 합니다: 1) 이메일 주소만으로 사용자를 조회합니다. 2) 데이터베이스에서 조회한 해시된 패스워드와 사용자가 입력한 평문 패스워드를 bcrypt.compare와 같은 함수를 사용하여 안전하게 비교합니다.
